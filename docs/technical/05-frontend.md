# The Frontend

How `apps/web` renders the product: state architecture, the Pierre rendering foundations, and how each product surface maps onto them. Product behavior lives in `docs/product/`; the visual source of truth is [`docs/product/designs/`](../product/designs/README.md); this document is how it's built.

## State: the server owns it, atoms view it

Throughline adds **no new state-management library**. The reviewer's state of record — journeys, read state, PR lists, job progress — already lives in the server ([02](./02-domain-model.md)), and the starter's `@effect/atom-react` + push-bus architecture is precisely a client for that shape:

- **Server-owned state** arrives as unary fetches (immutable journey data) or snapshot-then-live streams (ingestion progress, read state, PR list), folded into atoms in exactly one place: `apps/web/src/state/journeyState.ts` is the renderer's only fold-and-subscribe layer, so there is a single file to read to know what the UI believes and where it got it. Reconnects replay snapshots; the UI can always be rebuilt from the wire.
- **Renderer-local state** is only ephemera: scroll positions, collapsed-narrative flags, the changed-files-filter toggle. Location — which PR, cluster, or file is open — lives in the URL (see Routing). React state and a few atoms suffice for the rest.
- Read marks are **server-confirmed rather than optimistic**: the click issues `readState.markFile`, and the tick appears when the `readState.subscribe` stream delivers the authoritative document — the same stream that reconciles other windows. The round trip is to a process on the same machine, and the honesty is worth the frame it costs: a tick that drew itself and then disappeared would put the coverage guarantee in doubt, which is the one thing the mark exists to make tangible. A failed persist says so where the reviewer clicked — "a read mark did not save, so it is not counted yet — mark the file again" — instead of leaving behind a tick that never stuck.

The judgment call, made: a second store (Zustand/Jotai) would duplicate what atoms already do here, and server-owned state is what makes "leavable" and multi-window coherence free. If atoms ever chafe, the seam is thin — atoms are only the fold-and-subscribe layer.

## Rendering foundations

Every diff surface is `@pierre/diffs` (React bindings); every tree is `@pierre/trees`. Committed integration points, from their actual APIs:

- **The cluster page's middle panel is one `CodeView`** — its virtualized multi-file stack is built for exactly this. Items: one `diff` item per file in the cluster's `fileOrder`, built with `processFile(patch, { isGitDiff, oldFile, newFile })`. Unchanged regions collapse by default with in-place expansion — the product's expand-context interaction is native behavior, but only under one condition: a file must be parsed **with** its full old and new contents, which is what makes `isPartial: false` and therefore makes expansion possible. A patch on its own always parses as partial and can never expand. That is why `journey.filePatch` and `journey.fileContent` are fetched together as one bundle (`fetchBundle` in `apps/web/src/state/journeyState.ts`) rather than the patch first and the contents on demand: serving them apart would quietly cost the product an interaction the design promises, and would do so silently, because a partial file renders perfectly well and simply refuses to open.
- **Display modes** map directly: inline → `diffStyle: "unified"`; split → `diffStyle: "split"`; **just-the-code** → the same `CodeView` with `file` items (head-revision contents from `journey.fileContent`) instead of `diff` items, changed regions marked in the margin by the same `data-tl-*` markers emphasis already writes — a 3px inset rule per row, accent for this cluster's hunks and neutral for foreign ones, from `JUST_THE_CODE_CSS` in place of `EMPHASIS_CSS`. A plain-file item has no changed rows at all — every row's `data-line-type` is `context` — so there the markers land by line range alone. Annotations in this mode are spent on home labels and hints, not on the margin markers. One mode journey-wide, restored from `ReadState.displayMode`; the top bar's Diff | Code toggle and the file headers' inline/split control both set that one mode — placement is reach, not scope (product 04).
- **Line anchors** — cluster labels on foreign hunks, resurfacing marks, hint anchors, read-mark affordances — ride `lineAnnotations` + `renderAnnotation` (each annotation is `{ side, lineNumber, metadata }` rendering arbitrary React). Navigation ("one click from its home cluster", hint-click) rides the `CodeViewHandle.scrollTo` targets.
- **Changed-region navigation** — the `n`/`p` keystrokes walk the open file's changed regions via the same `scrollTo` targets on both reading surfaces. The file screen's footer names the position ("region N of M", or the plain count until the reviewer has stepped anywhere, because claiming region 1 before anyone was taken there would be a readout that is simply untrue); the cluster page's footer prints the keys and leaves the tally to the cluster header. The walk is deliberately _not_ identical in every display mode, because it cannot be: a pure deletion has no new-side line, so in just-the-code — where only the head revision is on screen — those regions drop out of the walk and out of their labels rather than being pointed at somewhere they are not. The one exception is a deleted file, which falls back to its deletion diff and therefore still has an old side to walk.
- **Emphasis and dimming** carry the cluster boundary: homed hunks emphasized (the product's single accent use), foreign hunks dimmed and labeled. Pierre has no per-range dim prop, and every file it renders lives in its own shadow root, so neither a global stylesheet nor a `className` can reach a code row. This was called out as the frontend's one integration risk and was spiked against a real `CodeView` before the reading experience was built; the mechanism it settled on is `apps/web/src/journey/emphasis.ts`: the `onPostRender` callback hands over the host element and therefore its shadow root, `data-*` markers are written onto the rows, and one memoised `unsafeCSS` stylesheet injected into that shadow root styles them. Marking feeds the library's own `--diffs-decoration-bg`, so the accent joins the diff's colour language instead of overwriting hover, selection, and the addition/deletion tint. [ADR 0010](../adr/0010-emphasis-marks-rows-through-the-one-seam-pierre-diffs-exposes.md) records the two constraints a reimplementation would otherwise rediscover the hard way — `data-line` is the row's own-side number, and marker attributes must always be written on both branches because container hosts are pooled across files.
- **Non-textual changes** render as honestly as the library allows. `@pierre/diffs` has no binary or image support at all — no item kind, no `binary` flag on a parsed diff — so a binary change, image or not, becomes a `file` item whose one line of contents _is_ the quiet placard naming it: "binary file added — 4.2 kB", "binary file changed — 12.3 kB → 15.1 kB". No image pair is drawn, and that is the trade taken deliberately: keeping every change inside the one virtualized scroll container and in narrative order is worth more than rendering it natively, and `journey.fileContent` already carries `oldImageDataUrl` / `newImageDataUrl` for the day the surface can afford to. Pure renames and mode changes read as single labeled rows, their home label anchored above the file's first line, because a file-level hunk has no line range to point at ([02](./02-domain-model.md)). All of them mark read and count toward coverage exactly as a diff does. Deleted files render in their clusters as deletion diffs, and appear as ghosted rows when the changed-files filter is on; the full tree stays the head revision.
- **The file tree** is a `FileTree` model over the full head-revision path list (`journey.tree`) — the project's real tree, per the product. Changed-file markers use the built-in git-status lane (`setGitStatus`), neutralized to one quiet dot per change because this product spends color on one thing only; the single per-row extra is the home-cluster count via `renderRowDecoration`, drawn only above one ("2 clusters"), since "1 cluster" is the unremarkable case and a lane full of it is noise. Read state is deliberately absent from the tree — it rides the file screen's own tab markers, where the file is actually open. The changed-files filter is `resetPaths` between full and changed-only sets; the pinned overview entry renders above the tree in the header slot.
- **Theming**: Shiki dual themes (`{ dark, light }` + `themeType`) follow the app's existing theme plumbing (`useTheme`); trees are themed to match via CSS variables. One accent color, as the product demands.

## Surface by surface

**Welcome** — folds `github.subscribePrs` (the snapshot-then-live PR list, already enriched server-side with each PR's journey state and with hidden and dismissed PRs filtered out) + `harness.status` + local `prState` into one list, with `github.refreshPrs` behind both freshness triggers. Ingested PRs carry derived journey progress; parked states ([03](./03-github.md): `gh` missing, rate-limit parked; [04](./04-analysis.md): no harness) render as calm, instructive banners. Refresh is on-focus and manual only — the no-polling rule is a UI rule too.

**Ingestion transition** — a direct rendering of the `ingestion.subscribe` stream: the displayed stages are a grouped view of the job's phases, the live activity lines and counters render the `analyzing` payload ([04](./04-analysis.md)), and there is no invented progress because there is no other data source. Reconnect mid-run replays the snapshot and the transition resumes where reality is.

**Overview** — `journey.overview` rendered as a document across the middle panel's full width: `ReadingPanels` is given no right panel at all, because guidance is a companion to _code_ and this page has none, and the prose is held to ~72ch so the measure stays readable instead of stretching to the window. Markdown with `tl:` links resolved to navigation, map entries joined with per-cluster derived scale and live progress. The PR's own words sit collapsed at the bottom, from `journey.get` metadata.

**Cluster page** — narrative block (collapsible, `tl:`-linked) above the `CodeView` described above. Mark-read is one interaction, two homes: a per-file affordance in the file header (`renderCustomHeader`) and a keystroke; marking collapses the item (`collapsed`) and advances every progress display through one derivation (`@app/journey/progress`).

**Guidance rail** — hints for the open cluster, positioned by anchor. Scroll-sync is viewport-driven at file granularity: on scroll the reading surface asks the library which items it currently has rendered (`getRenderedItems()` — the library already answers the viewport question, so there are no intersection observers) and reports those paths, and the rail floats the hints anchored to a file on screen to the top and reads them at full strength, leaving the rest in anchor order underneath. Prominence is spent on position, never on color, because the accent belongs to the open cluster's hunks and to nothing else. Clicking a hint scrolls the code via `scrollTo`. Hints anchored only to the old side are omitted in just-the-code — except on a deleted file, which has no head revision to show in silence and so renders as its deletion diff there, keeping an old side for its hints to bind to ([02](./02-domain-model.md)). The omission is said out loud at the foot of the rail, because a hint that silently disappears is worse than one that explains its absence. The rail is collapsible and the page is complete without it, per the product.

**Free file reading** — opening any file from the tree renders its full diff with every hunk labeled by home cluster; same read state, same marks, viewed from the file side. Open files sit in tabs — renderer ephemera; the URL holds only the active file. Files outside the changed set are served from the repository clone ([03](./03-github.md)).

**Settings** — detected harnesses with install/auth state (`harness.status`) and the active-harness selection (`settings.update`), plus theme. Calm, one page; T3 Code's provider settings page is the shape reference ([04](./04-analysis.md)).

## Routing

**TanStack Router**, with a **code-based route tree** — a handful of routes doesn't earn the file-based codegen plugin, and migrating to it later is mechanical. Browser history works in both hosts: the server already serves an SPA `index.html` fallback for unknown paths, and the packaged renderer is served same-origin by the local server (ADR-0004), so reloads and back/forward land correctly everywhere.

```
/                              welcome
/settings                      harness selection, appearance
/pr/$owner/$repo/$number       journey layout — resolves the journey; renders the
  │                            ingestion transition while one is running or absent
  ├─ /                         overview
  ├─ /cluster/$clusterId       cluster page
  └─ /file/$                   free file reading (splat: file paths contain slashes)
```

Params are typed end-to-end (TanStack's headline feature), so navigation from `tl:` links, the left rail, and hint clicks all go through one typed `navigate` surface. The rule of thumb: state that should survive a reload is in the URL; state that shouldn't (scroll, toggles) never is.
